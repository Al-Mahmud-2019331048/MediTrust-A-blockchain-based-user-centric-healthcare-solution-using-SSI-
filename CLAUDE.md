## How to Present Changes for Approval

Before making any code change, file edit, or running any Bash command that changes something (installs, deletes, commits, pushes, generates, migrates), always provide:

1. **What I'm doing** — plain English description of the change, no jargon
2. **Why** — what problem it solves or why it is needed
3. **What files are affected** — which files are being created, modified, or deleted
4. **What stays the same** — what is not being touched
5. **Any risks or things to watch** — anything that could go wrong or needs attention

**Exception:** Read-only commands (`git status`, `git log`, `ls`, `tsc --noEmit`, `git diff`) look at things and change nothing — no approval needed for these.

## What This Project Is

A thesis continuation implementing a **decentralised, patient-centric healthcare SSI system** with 10 required modules and 8 measurable experiments.

- **Identity layer:** Hyperledger Indy (BCovrin TestNet) + Credo-TS 0.5.x (AnonCreds, DIDs, ZKP selective disclosure)
- **Storage layer:** Full DWN node (LevelDB embedded — no external DB server) — patients own their encrypted records on their own machine
- **Encryption:** AES-256-GCM at rest + per-record key wrapping. SHA-256 integrity hashing already exists.
- **Consent:** DWN Permissions interface (enforces access) + Verifiable Consent Receipt VC on Indy (cryptographic proof)
- **Audit:** Signed, structured, persistent audit log (SQLite via Prisma — file-based, no server)
- **Key recovery:** Shamir Secret Sharing (5 shares, any 3 recover) + MPOA multi-party approval
- **No MongoDB anywhere** — eliminated entirely from the architecture

The legacy PoC (`demo/credo/` + `interface/`) is kept as reference. All new work goes into the top-level folders.

## The 8 Required Experiments

| Experiment                     | Metric   | How to Measure                                                          |
| ------------------------------ | -------- | ----------------------------------------------------------------------- |
| VC issuance time               | ms       | `POST /issue-credential` → `credential-issued` state                    |
| VC verification time           | ms       | `POST /send-proof-request` → `isVerified: true`                         |
| Blockchain transaction latency | seconds  | Schema/credDef registration on BCovrin                                  |
| DWN storage overhead           | KB/MB    | Encrypted record size vs plaintext size ratio                           |
| Selective sharing overhead     | ms       | Full record retrieval vs Protocol-filtered retrieval                    |
| SSS recovery time              | ms       | `initiateRecovery` to MEK reconstructed (3 shares) — already captured  |
| Key recovery success rate      | %        | N runs with valid threshold → pass; N runs with <3 shares → correct fail |
| Access revocation time         | seconds  | `DELETE /revokeAccess` → subsequent read returns 403                    |

**Bonus metric** (already built): SSS split time (ms) via `splitTimeMs` in `splitMEK()`.

**Attack simulation scenarios** (Day 18 benchmark — 5 scripted cases):
1. Read record without a permission grant → expect 403
2. SSS reconstruction with only 2 shares → expect thrown error
3. MPOA recovery attempt before all 3 approvals → expect 403
4. Expired MPOA request reconstruction attempt → expect 403 (status auto-set to `'expired'`)
5. Tampered audit entry verification → `AuditService.verify()` returns `false`

Results go in `benchmark/results/` as JSON + Markdown table.

## PoC Completeness Assessment (as of the backup-provider work)

Asked directly: "can we say the PoC is complete?" — the honest answer is **broadly yes**, with a specific list of exceptions that should be stated explicitly in the thesis rather than left for someone else to discover.

**All 10 required modules are built, and every one has been proven with a real, live test at some point in this project — not just written and assumed to work:**

| # | Module | Status |
| - | ------ | ------ |
| 1 | SSI Identity Layer | Done |
| 2 | Verifiable Credential System | Done |
| 3 | Digital Wallet | Done (via Bifold/BC Wallet) |
| 4 | Selective Sharing | Done — both the ZKP pathway and DWN field-redaction pathway, now exercised by pharmacy's and doctor's read UIs |
| 5 | DWN Implementation | Done — Records, Permissions, Protocols all real and live-tested |
| 6 | Encryption Layer | Done — real per-patient key, not a placeholder anymore |
| 7 | MPOA + SSS Key Recovery | Done — both self-custody and institutional paths live-tested |
| 8 | Consent Management | Done — real, patient-signed consent receipts |
| 9 | Audit Trail | Done — persistent, signed, tamper-detection proven live |
| 10 | Security Evaluation | Done — 8 experiments attempted, 5 attack simulations, all passing |

**The 8 required experiments: 6 produce genuine measured numbers; 2 are honestly reported as blocked, not faked.** Blockchain transaction latency and VC verification time can't run for a reason outside the code — the network this was built on blocks the raw connection needed to actually reach the identity ledger's validator nodes (confirmed directly via a port-level test, not a guess). The system correctly reports `status: 'blocked'` with the real underlying error for these two rather than fabricating a number — a defensible, honest way to report it, not a hidden failure.

**What's genuinely still open — state these out loud, don't let them be found:**
- **The device-level secret protecting every patient's individual key is still one single, un-split secret** (`DWN_MASTER_KEK`) — a known, named limitation, not yet fixed.
- **Real phone testing surfaced one wallet-compatibility issue** — BC Wallet specifically rejected the connection. Diagnosed with a strong theory (plain-HTTP endpoint / missing DidExchange handshake protocol) and worked around with a different wallet build (a generic Bifold APK), but the root cause was never conclusively fixed and re-tested against BC Wallet itself.
- **No deployment packaging** (`infra/docker-compose.yml`, the piece that would start every service with one command) was ever built — not required for a PoC, but worth naming as unfinished.

**Resolved this session (previously listed above as open):**
- **On-chain anchoring** — built. `BaseAgent.anchorHash()` + government-only `POST /anchor-hash` genuinely attempt a raw Indy `AttribRequest` ledger write for the 5 patient-signed audit event types (`consent_granted`, `consent_revoked`, `key_split`, `key_reconstructed`, `dwn_restored`), fire-and-forget so the caller's own request is never slowed down. Live-tested: correctly reports `anchorStatus: 'blocked'` with the real underlying pool-timeout error — same honest degradation as everywhere else, not a fabricated success. See Known Constraints for the full build/fix history, including a real regression (awaited anchoring turned a ~5ms revokeAccess call into ~5s) caught and fixed via live benchmark testing before this was called done.
- **The Healthcare-Authority 3-tier credential chain is back.** Rebuilt from scratch (the earlier build/revert cycle was never committed to git, confirmed via `git log` — no history to restore from) per explicit user instruction to reverse the "2-tier" locked decision. See the updated "DID hierarchy" Key Decision and Known Constraints.
- **MPOA reconstruct now verifies share-to-request binding.** `POST /sss/recovery/initiate-with-split` ties a request to the specific shares issued for it; the reconstruct route rejects shares that don't belong to the approved request's own manifest. Live adversarial-tested: shares from an unrelated split are now correctly rejected (403) against an approved, unrelated request — previously would have silently succeeded. See Known Constraints.

**The honest verdict:** for what a proof-of-concept is meant to demonstrate — that the architecture works and the hard parts (encryption, selective sharing, dual-path key recovery, tamper-evident audit, and the self-run backup provider replacing the last centralized dependency) are provably functioning, not just described — this is complete. What makes it a strong thesis rather than a shaky one is presenting the exceptions above exactly as they already are: clearly labeled, deliberate, or environment-caused limitations, sitting next to a system that's been adversarially tested and has caught its own bugs multiple times over.

**Separately, on the "decentralized" claim specifically:** the identity/credential layer (Hyperledger Indy, real multi-node consensus) is genuinely decentralized. Everything else — the DWN vault, the backup provider, the agents — is **patient-controlled**, not decentralized in the strict architectural sense: each is a single server process, not a distributed/replicated network. These are two different, both-true claims and should be stated separately in the thesis, not conflated into one blanket "fully decentralized" statement. The backup-provider work improved *centralization dependency* (moved off Google, a large company, onto self-run infrastructure) without making that layer *architecturally decentralized* (it's still one server) — a real, meaningful improvement, just not the same claim.

## DWN Record Schema

**Required DWN functions (from PoC requirements):**
`createRecord()` / `storeRecord()` / `queryRecord()` / `shareRecord()` / `revokeAccess()`
Internal names: createRecord, readRecord, grantPermission, revokePermission — HTTP routes expose the required names.

```typescript
// Records (stored in LevelDB under key: `record:{recordId}`)
{
  recordId: string,          // UUID
  patientDID: string,        // "did:indy:bcovrin:test:..."
  recordType: string,        // "medical" | "prescription" | "lab_report"
  protocol: string,          // which protocol governs this record type
  contentType: string,       // "application/json" | "application/pdf" | "image/jpeg" | "image/png"
  fileName: string | null,   // original filename for binary files, null for JSON records
  fileSize: number,          // byte size of plaintext before encryption
  encryptedData: string,     // AES-256-GCM ciphertext (base64)
  encryptedKey: string,      // AES key wrapped with patient public key (base64)
  iv: string,                // GCM initialization vector (base64)
  tag: string,               // GCM auth tag (base64)
  hash: string,              // SHA-256 of plaintext (integrity) — also anchored on Indy as VC
  integrityVCId: string,     // Indy VC ID containing hash + recordId (on-chain proof)
  createdAt: string,         // ISO8601
  updatedAt: string          // ISO8601
}
// API read responses include a computed accessPolicy field derived from Permissions:
// { ..record, accessPolicy: { "doctor": true, "insurance": false } }

// Permissions (stored in LevelDB under key: `permission:{permissionId}`)
{
  permissionId: string,
  patientDID: string,
  grantedToDID: string,
  recordType: string,        // "medical" | "prescription" | "lab_report"
  allowedFields: string[],   // ["prescription"] or ["diagnosis", "labResults"]
  purpose: string,           // "treatment" | "dispensing" | "insurance"
  grantedAt: string,
  expiresAt: string | null,
  revokedAt: string | null,
  consentVCId: string,       // ID of Consent Receipt VC on Indy
  actorRole?: string,        // "doctor" | "pharmacist" | "insurer" — only trusted alongside roleProofRecordId (Days 11-12)
  roleProofRecordId?: string // verified AnonCreds proof backing actorRole; grantPermission() rejects actorRole without this
}

// Protocols (stored in LevelDB under key: `protocol:{name}` — one row per name, Days 11-12)
{
  name: string,              // "MedicalRecord" | "Prescription" | "InsuranceClaim"
  actorRole: string,         // "doctor" | "pharmacist" | "insurer"
  allowedFields: string[],   // fields this role may read; empty = unrestricted
  createdAt: string,
  updatedAt: string
}
```

### Why we're doing this, in plain English

Two honest problems came out of just asking hard questions about a system that already existed:

**First**, every patient's medical records are currently locked with one single key — the *same* key for every patient in the whole system, sitting in a config file (`DWN_MASTER_KEK`). And the "3 people can rebuild a lost key" recovery system that was already built (`crypto/sss/`) has, this whole time, only ever practiced on a fake, made-up key in tests — never the real one actually protecting anyone's data. Two working pieces, never introduced to each other. Never flagged as a known placeholder anywhere in CLAUDE.md before this conversation, unlike every other similar gap in this project.

**Second**, there's no backup at all for the actual medical records themselves — only, in theory, for the key. If the one computer holding those records is ever lost, stolen, or destroyed, everything on it is gone permanently, no matter how well the key gets recovered. A recovered key with nothing left to unlock is useless.

### How we're fixing it, in plain English

Every patient gets **their own personal key**, created the moment they first use the system — not shared with anyone else. That key can be recovered two different ways, for two genuinely different real-life situations:

- **"I lost my own phone"** — the ordinary case. The key is split into 3 pieces, and all three go only to things the *patient themselves* owns: their phone, a printed paper backup kept somewhere safe, and a second device. Any 2 of the 3 rebuild it. No hospital, no company, no outside party is ever involved or needs to approve anything.
- **"The patient can't act for themselves"** — a genuinely different, rarer situation: unconscious, incapacitated, a minor. For this, the system keeps its existing "3 trusted people must agree" process exactly as it already works (`crypto/sss/`'s MPOA module) — untouched, just finally pointed at the real key instead of a fake one.

For the actual data — not just the key — every time something new is added or changed, a small, locked copy of just that one change gets sent immediately to the patient's own Google Drive. Nothing else gets re-sent, just that one new piece, so nothing is ever more than a moment out of date. If the patient's device is ever destroyed: rebuild the key from 2 of the 3 personal backups, pull every one of those small locked files back down from Drive, unlock them in order, and everything reappears exactly as it was — through a simple, guided app experience (scan a QR code, connect a second device, sign into Google, watch a progress bar), never by manually touching any of the underlying mechanics.

### Why we can honestly say "decentralized" and "patient-controlled"

Nobody but the patient can ever read or restore their own records — not a hospital, not this project's own servers, not anyone. That's the "patient-controlled" part, and it's real, not just a design intention — provable by the fact that no one else ever holds a usable piece of the key or an unlocked copy of the data.

The honest caveat, stated plainly rather than glossed over: using Google Drive means leaning on one large company for *keeping the locked files safe*, even though that company can never *read* them. So the fair, precise claim is **"patient-controlled,"** which is fully true here. **"Decentralized"** in the strict sense is only fully earned by the identity/credential layer (real Hyperledger Indy, real multi-node consensus) — for the data-recovery system described in this section, it's a partial claim at best, since one of the two backup destinations (Google Drive) is a single centralized provider. Keep these as two separate, precise claims in the thesis rather than one blanket statement.

Both recovery mechanisms (self-custody and MPOA) split the *same* underlying secret independently — mathematically sound, since Shamir shares reveal nothing below the threshold regardless of which independent share-set they belong to. See "Part A implementation status — Done" and "Healthcare-Authority reversion — Done" above for exactly what was built and live-tested for both of these.
